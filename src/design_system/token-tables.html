Using these tokens

Where a utility class exists, use it instead of a raw token. Reach for a token only when no utility or component class covers the need.

SCSS variable or CSS variable?

The short version: SCSS to configure, CSS to apply.

Use the SCSS variable only where the compiler has to see the value. That means as an argument to a Sass function or mixin, inside maps and @if or @each logic, in media query conditions, and when configuring Bootstrap, which reads variables such as $primary before it emits anything. These are cases where var() cannot work at all: rgba($ucl-lake-light, 0.8) computes a colour, while rgba(var(--ucl-lake-light), 0.8) does not.

Use the CSS variable everywhere else — that is, whenever you are simply applying a value to a property. It survives into the compiled stylesheet, so anyone inspecting the page can trace a colour straight back to the token that produced it, which an SCSS variable makes impossible because it is gone by the time the browser sees the CSS. It can also be overridden per scope or per component instance, it responds to [data-bs-theme], and it is the only form available to anyone consuming the compiled CSS from outside this repository.

The trade-off is that var() has no compile-time safety: a misspelled custom property produces no error, just no style. Where a missing value would break layout rather than merely look wrong, give it a fallback — var(--ucl-maroon, #800000).

Reading the tables

Brand tokens carry no utility classes by design. They are the raw palette; components should consume the semantic tokens that sit on top of them, so that a change of brand colour propagates rather than needing to be chased through every component.

A dash means the data does not exist rather than that it is missing: no custom property is published, no utility class is generated, or no note has been written yet.

Bootstrap's theme colours are only partly semantic. Primary, success, info and warning name a role, but secondary, light and dark name an appearance and so tell you nothing about when to use them. A fully semantic name would read more like subtle text on a dark surface. Treat the appearance-named slots as Bootstrap's vocabulary rather than as this system's roles.

Documenting a token

The generator reads four comment forms in _variables.scss. Any other comment is treated as an ordinary code comment and ignored, and a token with no annotation still appears in the table with empty cells.

Comment conventions read by the token generator
Comment form Effect
// == Section Name == Starts a section. Groups every token that follows until the next section marker.
//! guidance Guidance prose for the current section, shown above its table.
/// note Note for the single token declared immediately below.
// note at the end of a declaration Note for that token. The inline equivalent of ///.

Sections route to a tab by type: colour tokens land in Colors, everything else in Other Tokens. Build flags such as $enable-dark-mode are excluded, since they configure the build rather than describe the design.
